# alpha12 验证记录

2026-10-10，versionCode 12。继续 E05 系统时间验收。

## 实际问题与修复

API 29 自建 AOSP 模拟器上，将系统时区从 UTC 改为 America/New_York，原组件仍显示 `示例数据 · 06:59`，未变为 `01:59`。新增系统广播接收器后，广播确实送达，但因额度／设置参数不变，Compose 跳过时间文本重绘，原断言仍失败。

最终实现接收 TIME_SET／TIMEZONE_CHANGED，发布独立时间变化信号，让组件与前台额度页面重新格式化缓存时间。广播处理限制 8 秒并保证结束，不获取额度、不清空成功快照。前台现有 30 秒时钟在信号到达时立即重启读取。

## 设备证据

显式 `SystemTimeDeviceTest` 在真实系统时钟／时区上验证，通过（3.514 秒）：

- UTC→纽约：缓存成功时间 `06:59`→`01:59`，没有主动调用组件 update 来帮助断言。
- 2026-03-08 夏令时：到期时刻正确格式化为 `03/08 03:00`，跨过实际重置时刻后显示“重置待确认”，额度仍为 62%。
- 实际时钟跨天：缓存 fetchedAt 保留，不把时间流逝当成新额度。
- 真实已连接合成账号时钟回拨 120 秒：非强制 refresh 发出一次新请求并从 38% 已用更新为 17%，没有因未来缓存时间而一直跳过。

测试 finally 恢复原时间（按单调时钟补偿测试耗时）、原时区和自动设置；外部检查已确认 Asia/Shanghai、auto_time=1、auto_time_zone=1。所有账号／网络均为测试 runner 拦截的合成数据。

CI 会在普通套件及独立生命周期回归后执行 `scripts/system_time_smoke.sh`，保存原始 runner 报告并验证实际成功码。普通套件对此需要明确授权的改时探针条件跳过。此结果覆盖 AOSP API 29；其他设备版本及小米仍需各自验收。

最终完整 API 29 普通套件通过（124.365 秒，18 项实际成功、3 个条件探针跳过），独立系统时间脚本也执行成功（5.474 秒）。最终构建／lint／47 项 JVM 测试通过。
